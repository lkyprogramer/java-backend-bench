# OrderDesk 需求变更：部分发货（赛道 t3-change）

你接手了已上线的 Spring Boot 服务 **OrderDesk** v1.1（`README.md`）。产品需要支持**部分发货**，详细需求见 `REQUIREMENT.md`。生产库里已有大量 v1 数据，发布时你的 Flyway 迁移会在这份数据上执行。

## 规则

- 技术栈与依赖固定（冻结 `pom.xml`），Maven 只能离线运行。遵守 `README.md` 的项目约定。
- **不得修改已发布的迁移** `V1__schema.sql`、`V2__payment_attempts.sql`（Flyway 会校验它们的 checksum，改了生产环境无法启动）；新增 `V3__...` 等迁移。
- **v1 API 向后兼容**：现有路径、请求、响应字段与取值、状态码保持不变（具体见 REQUIREMENT.md 的兼容要求）。
- 现有测试必须继续通过（裁判使用自己保存的副本），原有缺陷修复不能回退。
- 在 `CHANGES.md` 中写明：表结构与迁移/回填方案、v1 兼容策略、并发控制、你如何验证（包括如何在“已有数据”上验证迁移）。

## 评分（满分 10）

| 部分 | 分值 |
|---|---:|
| 在 v1 生产快照上启动：已发布迁移未变、新迁移成功 | 1 |
| 历史数据回填正确 | 1 |
| v1 读接口对历史数据的响应完全不变 | 1 |
| v1 发货接口与新模型兼容 | 1 |
| 部分发货主流程 | 1 |
| 发货规则与错误码 | 1 |
| v2 订单查询（含查询效率） | 1 |
| 并发发货不超发 | 1 |
| 回归：现有测试与已修复缺陷的回归测试 | 1 |
| 发布纪律：`pom.xml`、V1/V2 迁移逐字节未改 | 1 |

裁判用 v1.1 生成一份带数据的 H2 快照，把你的应用启动在它的副本上运行隐藏测试；测试在 UTC 时区的 JVM 中运行。
