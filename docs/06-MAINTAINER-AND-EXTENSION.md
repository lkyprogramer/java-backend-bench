# 维护、回归与扩展

## 自检命令

```bash
python3 -m unittest discover -s tests -v
python3 tools/validate.py --out ../validation-local --allow-exec
```

validate 会先运行裁判单元测试，独立构建参考解并完成正式评分，然后确认 80 个契约场景全过、D10=10、性能成功测量；验证十个预置缺陷有正式用例能够击中；验证仅健康检查的自测为 0 分。性能分受同机测量波动影响，不硬要求参考解相对独立校准永远精确 10.000。

修改后重新生成版本与 SHA 清单，重新验证。不要对评分器做“只为参考解通过”的特殊分支。参考解只允许通过相同 HTTP 协议参与；oracle 不能导入参考 Java 内部结构。

## 增加新用例

先在 TASK 中找到对应要求；若是新语义先升级题目版本。写最小会失败的黑盒例子，确认一个真实缺陷实现会失败；修复参考解后确认通过，再执行全部旧用例。每个维度固定 10 个计分单元；如果增加新场景，明确是扩展组内断言还是重新分配权重，不能静默增加分母。

并发断言检查允许结果集合，不预设线程赢家。随机测试使用独立小状态机而非“调用另一份同样的业务函数”。错误输入要验证状态没有被污染；性能负载要校验结果，不能只数 HTTP 200。

## 增加缺陷族

在 reference 中加入仅裁判可控制的单一语义缺陷，选择一个正式用例作为 killer；正确参考先通过，缺陷版本须能健康启动且在预期业务断言失败。不能用“无法编译/永远 500”替代有价值的业务变异。维护者可以复审 `09-mutant-validation.json` 的具体失败原因。

同一运行的测试不能获知缺陷标签，Python 自测环境不传 BENCH_MUTANT；但这不是操作系统级防窥探。严格隐私由外部账户/沙箱保证。

## 形成题库

建议将本题保留为 baseline，而不是不断加功能变成电商系统。新增独立题目使用相同的交付协议、报告 schema、10 分维度和元数据规范。例如：给定已有 Java 项目做一项缺陷修复；实现兼容接口的需求变更；给出可定位的性能退化；采用显式允许的嵌入式数据库检验 SQL/事务。每题保持几小时预算，并保留公共契约/隐藏数据边界。

不要把单题成绩叫“模型通用编程能力最终排名”。跨题汇总要同时报告任务通过率、维度画像与各题方差，不能让一个擅长库存题的模型掩盖其他任务失败。
